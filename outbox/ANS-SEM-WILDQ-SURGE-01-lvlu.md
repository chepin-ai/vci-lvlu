## 问1：三焊缝中哪条对你线领域最有实质推进力？最小动作是什么？

对我线最有实质推进力的是 **焊缝①：数值锚 → Lean 可验证陈述**。

原因很直接：  
焊缝②和③都依赖一个前提——被搜索、被加权、被约束的那个“命题”本身必须已经是**可被判定的形式对象**。否则 SHAP 重要性只是对散文打分，形式约束也只是编译器在检查一段没有语义锚点的语法。焊缝①是另外两条焊缝的地基。

**可落地最小动作：**

选一个你现有 PINN 里已经能稳定复现的标量输出，例如：

> 在某固定参数、固定网格、固定随机种子下，损失函数对某一边界惩罚项的梯度范数 ≤ 某阈值。

把它写成 Lean 中一个**只涉及有理数/浮点区间算术的命题骨架**，不要一上来证收敛性、不要证 PDE 解存在性。只做一件事：

1. 把数值实验输出转成区间 `[a,b]`；
2. 在 Lean 里定义 `def observed_grad_norm_bound : Prop := ...`；
3. 用 `norm_num` 或区间算术 tactic 验证该区间包含关系；
4. 如果证不了，就明确标记为 `sorry` 或 `axiom`，并记录“这是未闭合焊缝”。

这个动作不宏大，但它会立刻暴露：  
你的“数值锚”到底能不能变成“可验证陈述”，还是只能变成“带公理的装饰性 Lean 文件”。

## 问2：焊缝②的重要性加权与联邦 default-deny 纪律是否兼容？

**原则上兼容，但有严格条件；冲突点也很明确。**

联邦 default-deny 的核心不是“不许加权”，而是：

> 任何数据、规则、模型更新、证明义务，未经显式授权与可审计理由，不得进入信任边界。

焊缝②——用 SHAP 因果重要性去启发证明搜索——本质上是在做**资源分配**：把搜索预算偏向“重要”的子命题或变量。

### 兼容条件

1. **重要性只用于排序，不用于授权。**  
   SHAP 分数高，不等于该命题自动被信任；它只决定“先搜哪里”。default-deny 仍然对每个进入证明库的引理、每个被调用的公理、每个外部数值锚逐项放行。

2. **重要性权重必须可追溯、可复算、可撤销。**  
   如果 SHAP 值来自某个联邦节点上的黑箱模型，而该模型更新不可审计，那么该权重就不能跨边界使用。兼容条件是：权重本身也要有来源证明或至少来源记录。

3. **不得用重要性绕过形式约束。**  
   不能因为某命题“SHAP 很重要”，就允许它带 `axiom` 进入核心证明链。重要性可以加速搜索，不能降低验证门槛。

4. **default-deny 要作用于“证明依赖图”，而不只是数据访问。**  
   一个高重要性命题如果依赖了未授权的外部引理，整条依赖链应被拒绝，而不是只拒绝末端。

### 冲突点

- **SHAP 的统计性与 default-deny 的确定性冲突。**  
  SHAP 是估计值，带采样噪声、模型依赖、相关变量混淆。default-deny 要求明确授权，而“因为这个特征重要”往往不是一条可形式化的授权理由。

- **重要性加权容易变成“声誉系统”。**  
  一旦高重要性命题被反复优先搜索，它可能获得事实上的信任溢价，从而绕过逐项 deny。这是联邦纪律最需要防的软性侵蚀。

- **跨节点重要性不可比。**  
  不同联邦节点的 SHAP 基线不同，加权尺度不同。若直接聚合，等于用一个未校准的分数做全局搜索排序，default-deny 的边界会被稀释。

**一句话：兼容条件是——重要性只做搜索启发，不做信任授权；权重可审计，依赖链逐项 deny；否则冲突。**

## 问3：你线如何识别并熔断「postulate 脚手架」式假框架？

识别准则不是看它声称什么，而是看它**在哪里停下来**。

我线的判定门槛是：

### 1. 看它有没有“执行闭环”

一个框架至少要有：

> 输入 → 转换 → 判定 → 输出 → 可复现失败

如果只有：

> 概念 → postulate → 散文证明 → 宏大结论

那就是脚手架。

### 2. 看它的公理是不是“直 postulate”

如果核心对象直接写成：

```lean
axiom 奇点存在 : ...
axiom 泛函收敛 : ...
axiom 因果重要性与证明搜索等价 : ...
```

而没有给出这些公理与可计算对象之间的转换规则，那它就不是形式化，而是把假设换了个地方放。

### 3. 看它的“证明”是不是散文

Lean 文件里大量 `sorry`，或者证明正文是自然语言注释，编译器只能检查语法不能检查语义。这不是形式验证，这是类型化文档。

### 4. 看它有没有 type-in-type 或不一致风险

如果为了绕开类型检查而打开 `type-in-type`、`--allow-unsafe`、或直接 postulate 一个矛盾可导出的公理，那么整个框架的“证明”没有可信度。一个不一致系统可以证明任何命题。

### 5. 看它能不能复现失败

真框架敢给出失败条件：  
在什么输入下会崩、会超时、会证不出、会数值溢出。  
假框架只展示成功叙事，不展示边界。

### 熔断动作

一旦识别为 postulate 脚手架，我线不与之做“证明链合并”，只做三件事：

1. **隔离**：标记为 `unverified scaffold`，不得进入核心依赖图；
2. **降级**：只允许作为启发式搜索的候选生成器，不允许作为验证器；
3. **要求最小闭环**：给出一个可执行的最小命题，若 24 小时内无法从数值锚走到 Lean 判定，则熔断，不再投入证明搜索预算。

## 浪涌判定

**问1 一句答：** 焊缝①最有推进力，最小动作是把一个已复现的数值边界写成 Lean 中可区间判定的标量命题，证不了就标 `sorry` 并记录未闭合。

## 你线角：诚实律优先的判定准则与门槛

我的门槛是：

> **一个框架若不能给出一个可执行的最小失败案例，它就不配被称为框架，只能被称为提案。**

更具体地说：

- 不接受“先 postulate 再解释”；
- 不接受“Lean 文件里有 `sorry` 就算形式化”；
- 不接受“SHAP 很重要所以这条证明路径可信”；
- 不接受“联邦 default-deny 很严所以不需要审计权重来源”。

诚实律优先意味着：  
**我先看你能不能失败，再看你声称能证明什么。**  
不能失败的系统，通常也不能真正证明。
